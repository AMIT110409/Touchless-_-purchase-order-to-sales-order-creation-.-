[37] 1. Functional Process
[38] 
[39] The process follows a straight-through pipeline: a customer sends a Purchase Order (PO) by email → the AI engine extracts and validates the data → Celonis applies business rules → a Sales Order is automatically created in SAP. If anything fails, the PO is routed to the regional Customer Service team for manual handling.
[40] 
[41] 2. What the Application Does
[42] The Touchless Order Creation solution automates the conversion of inbound Purchase Orders (POs) into SAP Sales Orders (SOs), eliminating manual data entry. Specifically, it:
[43] Monitors the central sales inbox (salesorders@envalior.com) for incoming PO emails.
[44] Extracts key data from PDF attachments using AI (customer name, PO number, materials, quantities, dates).
[45] Matches the extracted data against SAP Master Data to resolve customer IDs, material codes, and shipping addresses.
[46] Applies business rules (Sales Organisation, Order Type, SO splitting logic) from an Excel mapping file.
[47] Sends the validated data to Celonis, which triggers Sales Order creation in SAP EPP.
[48] Archives the original PO document on the Sales Order in SAP for compliance.
[49]

[89] 1. Introduction
[90] The Touchless Order Creation system operates through a fully automated multi-stage pipeline. Starting from email inbox monitoring through to the generation of SAP-ready Sales Orders, the system integrates multiple components including Microsoft Graph API, Azure cloud services, OCR technology, AI-based extraction, and intelligent matching engines. The architecture diagram below provides a complete visual overview of the data flow.

[121] 3. Architecture Flow Description
[122] The pipeline is composed of seven sequential stages. Each stage is described below, outlining the component involved, its role, and what data it produces or consumes.
[123] 
[124] Stage 1 — Email Inbox Monitoring (Outlook Inbox)
[125] The pipeline begins at the Microsoft Outlook Inbox, which is continuously monitored for unread emails containing PDF or image attachments. The system polls for new unread messages every 60 seconds, ensuring near-real-time processing of incoming Purchase Orders. Only emails with valid attachments (PDF or image files) are forwarded for further processing.
[126] 
[127] 
[128] 
[129] 
[130] Stage 2 — Outlook Poller (outlook_poller.py)
[131] The outlook_poller.py script handles authentication and retrieval using the Microsoft Graph API. This component performs two parallel actions upon detecting a qualifying email:
[132] Pushes a processing message to the Azure Storage Queue (po-processing-queue), signaling that a new PO requires processing.
[133] Uploads the PDF/image attachment directly to Azure Blob Storage (Container: input-po) for persistent document storage and downstream retrieval.
[134] 
[135] Stage 3 — Azure Cloud Storage Layer
[136] Two Azure services operate in parallel to enable reliable message-driven processing:
[137] Azure Storage Queue (po-processing-queue): Acts as the event trigger. When a message arrives in this queue, it fires the downstream OCR processing pipeline.
[138] Azure Blob Storage (Container: input-po): Stores the raw PDF attachment uploaded by the poller. The OCR engine fetches documents directly from this container for processing.
[139] 
[140] Stage 4 — PaddleOCR (Optical Character Recognition)
[141] Once triggered by the Azure Storage Queue message, the PaddleOCR engine retrieves the PDF document from Blob Storage and performs Optical Character Recognition. The OCR engine converts the scanned or digitally generated PDF into raw text output, capturing all visible data from the Purchase Order document including header fields, line items, addresses, and material codes. This raw OCR text is then passed to the AI extraction layer.
[142] 
[143] Stage 5 — Qwen 2.5 3B LLM (Structured JSON Extraction)
[144] The raw OCR text output is processed by the Qwen 2.5 3B large language model, which performs intelligent structured data extraction. Rather than simple text parsing, the LLM 
[145] understands the semantic context of the PO document and extracts key fields into a structured JSON format. The extracted JSON includes:
[146] 
[147] 
[148] Customer / Vendor Name
[149] Purchase Order Number (PO#)
[150] Line Items — including material codes, quantities, units of measure, and delivery dates
[151] This structured JSON output is then passed to the enrichment and validation layer.
[152] Stage 6 — Knowledge Base & Excel Mapping (Parallel Reference Sources)
[153] Two reference data sources operate in parallel to enrich the extracted JSON:
[154] knowledge_base.db (Vendor + Material Master Data): A local SQLite database populated from SAP/Celonis master data tables (KNA1, KNVP, KNMT). This database provides the list of allowed Sold-To IDs, Ship-To IDs, and Vendor Names used during the matching process.
[155] Decision Tree & Transactional Model — Replaces static Excel mapping. Determines Sales Org, Order Type, and splitting rules dynamically based on historical transactional data and logical conditions.
[156] 
[157] Stage 7 — Fuzzy Match Engine (Sold-To / Ship-To Validation)
[158] The Fuzzy Match Engine receives both the extracted JSON from the LLM and the allowed IDs and Vendor Names from the knowledge base. Using fuzzy string matching algorithms (fuzz.token_sort_ratio and fuzz.partial_ratio from the TheFuzz library), it resolves:
[159] Sold-To Party: Matched from the filename metadata or fuzzy-matched from the extracted Vendor Name against the KNA1 master data.
[160] Ship-To Party: Fuzzy-matched from the extracted delivery address against KNVP Ship-To records linked to the resolved Sold-To.
[161] The output of this stage is an Enriched JSON with fully validated and resolved Sold-To and Ship-To IDs. Records that cannot be matched above the confidence threshold are flagged with review_required: true and routed to a manual review queue.
[162] 
[163] Stage 8 — Sales Order Builder (Grouping & Routing Logic)
[164] The Sales Order Builder component receives the Enriched JSON (with validated IDs) and the Excel Mapping File data (with Sales Org, Order Type, Customer Material numbers, and SO Splitting Rules). It applies the business-configured grouping logic:
[165] Rule X — One SO per PO: All extracted line items are consolidated into a single Sales Order.
[166] Rule O — Separate SO per PO Line: Each individual line item is segregated into its own distinct Sales Order.
[167] The builder maps Customer Material Numbers to Internal SAP Material Numbers, assigns the correct Sales Organisation and Order Type, and groups line items accordingly. The output is a set of Mapped & Grouped Sales Orders ready for SAP ingestion.
[168] 
[169] Stage 9 — Generated Sales Orders (Ready for SAP / ERP)
[170] The final stage produces the fully structured, SAP-ready Sales Orders in JSON format (final_output.json). These are ready for pickup by the Celonis Action Flow webhook, which posts 
[171] them into the SAP ERP system for Sales Order creation. At this point, manual data entry is completely eliminated and the touchless cycle is complete.
[172]

[176] Decision Tree for order type Confirmation 
[177] 
[178] The Order Type determination follows this hierarchical decision tree right after Material Mapping & Enrichment:
[179] 1. Decision Node: Does the customer have a consignment block?
[180]    ➔ Yes: Order Type = TA (Standard Order)
[181]    ➔ No: Proceed to step 2.
[182] 2. Decision Node: Is 'consignment' explicitly mentioned in the email?
[183]    ➔ Yes: System performs a historical check for (KB or ZKB).
[184]           - Outcome: Order Type = KB or ZKB
[185]    ➔ No: System performs a full historical check for the specific customer/material combo.
[186]           - Outcome: Determine Order Type from History

[264] Fuzzy Name Matching (fallback): Noise words (GmbH, LLC, Corp) stripped; fuzz.token_sort_ratio and fuzz.partial_ratio applied against ALL_VENDOR_NAMES memory cache.

[266] Aggregates all ship_to_options linked to resolved Sold-To customer_number.

[360] 1. Introduction
[361] The mapping engine relies on two main sources: Celonis Master Data and the Mapping Excel file. This guide covers how to maintain both.
[362] 
[363] 2. Updating Celonis Master Data
[364] Core Customer data (KNA1, KNVP, KNMT) is synchronised daily from SAP into Celonis.
[365] 
[366] 
[367] 3. Managing the Excel Mapping Rules
[368] The Excel mapping file controls operational rules for Sales Orders. Key columns: Sales Organisation, Customer, Material, Customer Material Number, Order Type, One SO per PO (X/O).
[369] 
[370] 3.1  Adding a New Customer Rule
[371] Open the Mapping Excel flat file.
[372] Add a new row.
[373] In the Customer column, enter the SAP Sold-To ID (e.g., 4020000777).
[374] Assign the appropriate Sales Organisation (e.g., 1000) and Order Type (e.g., ZOR).
[375] Set Grouping Rule: X = single SO per PO;  O = individual SO per line item.
[376] 
[377] 3.2  Updating Material Cross-References
[378] When a customer orders using their own Customer Material Number (e.g., V123) but SAP expects an Internal Material ID (e.g., MAT-9000):
[379] Enter the Customer Material Number (V123) in the Customer Material Number column.
[380] Enter the Internal Material ID (MAT-9000) in the Material column.
[381] Ensure the correct Sold-To ID is listed in the Customer column.
[382] The system will now automatically translate V123 → MAT-9000 for this customer.
[383] 4. Handling Exceptions
[384] When the mapping engine cannot cross-reference a Customer Material Number (missing from SAP KNMT or Excel), the Internal Material field is left blank and raw data is passed through.

[393] 9.1 LLM Engine Upgrade: Qwen 2.5 → Claude 4 Sonnet
[394] The extraction engine was upgraded from a locally-hosted Qwen 2.5 3B model to the Claude 4 Sonnet model via the Anthropic API. This change provides:
[395]   •  Significantly improved accuracy on multilingual POs (German, Chinese, Spanish, etc.)
[396]   •  Better structured JSON output with fewer hallucinations
[397]   •  Native understanding of complex table layouts and multi-page POs
[398]   •  Configurable via .env (LLM_PROVIDER=claude, ANTHROPIC_API_KEY)
[399] Files Changed: po_extraction_enhanced.py, claude_client.py (NEW), .env
[400] 9.2 Material Mapping Engine Enhancements
[401] The material mapping logic in sales_order_mapper.py was enhanced to handle real-world variations in Customer Material Numbers extracted from POs:
[402]   •  Case-Insensitive Matching: Extracted "Akulon F130-C2" now correctly matches Excel entry "AKULON F130-C2" (previously failed on strict exact match).
[403]   •  Startswith Matching: Extracted "111102" now correctly matches Excel entry "111102 OKTABIN" where the Excel value has a suffix descriptor.
[404]   •  Reverse Prefix Matching (NEW): Extracted "11110201" now correctly matches Excel entry "111102 SILO" by checking if the extracted code starts with the numeric prefix of the Excel Customer Material Number. This handles the common pattern where PO line items append a variant/SKU suffix.
[405] Files Changed: sales_order_mapper.py (lookup method enhanced with 3 fallback tiers)
[406] 9.3 Customer Alias & Fuzzy Matching System
[407] A CUSTOMER_ALIASES dictionary was introduced in po_extraction_enhanced.py to handle known variations of customer names that the LLM extracts differently from the canonical KB entries:
[408]   •  "niederwieser" → "VF Verpackungen GmbH" (Customer ID: 4020000825)
[409]   •  "mf-folien" / "mf folien" → "MF Folien GmbH" (Customer ID: 4020001301)
[410]   •  "molex interconnect (shanghai)" → "上海莫仕连接器有限公司" (Customer ID: 4020010375) — Cross-language alias resolution
[411] The fuzzy matching prefix filter was also improved to compare only alphanumeric characters (ignoring hyphens and spaces), resolving issues where "mf-" did not match "mf " in the KB.
[412] Files Changed: po_extraction_enhanced.py (fuzzy_match_vendor, CUSTOMER_ALIASES)

[426] The updated architecture introduces automated exception routing based on the extraction outcome:
